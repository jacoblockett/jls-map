# Map CLI reference

The Map runtime is the supported command-line interface to a Map graph. It can be used by humans, agents, and external tooling without invoking the Map skill itself.

The CLI is the interoperability boundary for Map data. Consumers should use the runtime rather than reading or modifying `.map/db` directly. The Map skill adds the semantic workflow for authoring and clarifying intent, but read-only consumers do not need the skill workflow or its specialists in order to inspect an existing Map.

Examples in this document use `map` as the executable name. When Map is installed through JLS, use the installer-provisioned Map CLI path for the active platform.

## Quick reference

```text
map [--path PATH] [--config PATH] <command>
```

Top-level commands:

```text
init
create
relate
unrelate
set
replace
abandon
delete
get
show
context
status
validate
search
history
session
```

Use the runtime's built-in help for the exact syntax supported by the installed version:

```text
map --help
map <command> --help
map create <kind> --help
map get <kind> --help
map session <command> --help
```

`map --version` reports the installed runtime version.

## Public interface boundary

Map stores its embedded database under `.map/db`, but that database is an implementation detail. Do not inspect, query, edit, or replace it directly as an integration mechanism.

Use the CLI for all supported access.

For external consumers such as implementation planners, issue-tracker handoff agents, reporting tools, or repository automation, the normal boundary is read-only:

```text
status
validate
get
show
context
search
history
```

These commands expose authoritative graph state without requiring the `$map` workflow to be active.

The `session` data is recovery state for the Map workflow, not authoritative semantic state. External consumers should normally ignore it.

Commands that mutate semantic state are intentionally separate:

```text
init
create
relate
unrelate
set
replace
abandon
delete
```

An external handoff tool that only needs to understand a completed Map should not need any of those mutation commands.

## Output and errors

Normal successful runtime commands emit pretty-printed JSON to standard output.

For example, `map create intent ...` returns an object containing the new ID, while `map get intents` returns a JSON array of IDs.

Runtime failures are written to standard error in the form:

```text
map: <error>
```

and exit with a non-zero status.

Help and version output are generated by the command-line parser and are text rather than JSON.

### Important validation behavior

`map validate` is a semantic report, not merely a process-status check. An invalid graph is reported as JSON:

```json
{
  "ok": false,
  "errors": [
    "..."
  ]
}
```

Consumers must inspect the `ok` field. A graph with validation errors is reported through the JSON payload rather than by treating the validation report itself as a command failure.

## Map location

Map accepts two global location options:

```text
--path PATH
--config PATH
```

They may be used with normal commands such as:

```text
map --path /path/to/project status
map --path /path/to/project/.map status
map --config /path/to/.maprc status
```

`--path` may point either to a project root or directly to its `.map` directory.

For an existing Map, the selected location must resolve to an existing `.map` directory. Map does not silently initialize a missing graph.

### Location precedence

For existing Maps, path selection follows this order:

1. `--path`, when supplied.
2. `path` from an explicit `--config` file or directory.
3. `path` from `.maprc` in the current working directory.
4. The current working directory.

If an explicitly selected path does not contain a Map, the runtime fails. It does not fall back to another Map.

### `.maprc`

Map configuration uses TOML. The currently supported fields are:

```toml
path = "../project"
schema = "../map-runtime/schema.surql"
```

Both fields are optional.

Relative paths in a config file are resolved relative to the directory containing that config file. `~`, `~/...`, and `~\\...` are expanded using the user's home directory when possible.

`--config` may point directly to a config file or to a directory containing `.maprc`.

## Initializing a Map

```text
map [--path PATH] [--config PATH] init [--schema PATH]
```

Examples:

```text
map init
map --path /path/to/project init
map --path /path/to/project init --schema /path/to/schema.surql
```

The target may be either an existing project directory or a `.map` path whose parent directory already exists. Initialization creates the `.map` directory. It does not create missing project parent directories.

Initialization refuses to overwrite an existing `.map`.

### Schema selection

For `init`, the schema is selected in this order:

1. `init --schema PATH`.
2. `schema` from explicit `--config`.
3. `schema` from cwd `.maprc`.
4. The schema packaged with the installed Map runtime.

Initialization creates Map metadata with:

```text
depth:  mvp
stance: normal
```

It also creates the Map's local project identity.

A successful initialization returns JSON containing at least:

```json
{
  "ok": true,
  "path": ".../.map",
  "schema": ".../schema.surql",
  "schemaVersion": "2",
  "runtimeVersion": "...",
  "projectId": "..."
}
```

## On-disk identity

A Map contains a local project identity at:

```text
.map/project.json
```

The project ID is generated at initialization and is preserved when the Map is moved or copied. Normal runtime commands require a valid project identity to be present.

The embedded database lives under:

```text
.map/db
```

`project.json` identifies the Map. `.map/db` contains runtime-managed state. Neither should be rewritten by external consumers.

## IDs

New graph nodes receive opaque 20-character IDs containing lowercase ASCII letters and digits.

Example shape:

```text
7k2h8s4m1p9x3q6v0abc
```

Treat IDs as opaque strings. Do not infer meaning from them.

Use bare IDs in CLI commands unless a command's built-in help explicitly documents another form.

### Replacement-aware IDs

Map supports replacement history. Most semantic commands that resolve a current node can accept a historical node ID and transparently resolve it to the current replacement target.

For example, after replacing decision `OLD` with decision `NEW`:

```text
map show OLD
```

returns the current `NEW` decision.

Use `history` when the replacement chain itself matters.

`delete` is intentionally more literal because it removes stored records and replacement metadata. `history` also operates on the supplied history ID rather than treating it merely as a current-node alias.

## Semantic model

Map has five node kinds:

| Kind | Purpose |
| --- | --- |
| `intent` | A goal, desired outcome, or scoped objective |
| `question` | A material unresolved decision or clarification |
| `decision` | A settled or provisional answer/choice |
| `idea` | A possible concept that is not itself a settled decision |
| `fact` | Contextual evidence or established information |

Map has five relationship kinds:

| Relationship | Meaning |
| --- | --- |
| `contains` | An intent contains a child intent, question, or decision |
| `answers` | A decision answers a question |
| `depends_on` | An intent depends on another intent, or a question depends on another question |
| `fact_context` | A node is associated with a fact |
| `idea_context` | A node is associated with an idea |

Relationship kinds are inferred by `relate` and `unrelate`; callers do not provide the table name directly.

## Creating nodes

### Intent

```text
map create intent <INTENT> [--context TEXT] [--depth mvp|thorough] [--stance normal|adversarial]
```

Example:

```text
map create intent "Add account recovery"
```

An intent starts with:

```text
explored = false
closed   = false
```

`--depth` and `--stance` are optional intent-level overrides. If omitted, the intent inherits the Map-level values.

### Question

```text
map create question <QUESTION> --intent <INTENT_ID> [--reason TEXT]
```

Example:

```text
map create question "How long should reset links remain valid?" \
  --intent 7k2h8s4m1p9x3q6v0abc \
  --reason "Expiry affects security and recovery UX"
```

The parent must be a current, non-abandoned intent.

Creating the question also creates its `contains` relationship to the parent intent. A new question starts with `asked = false`.

Adding unresolved work beneath a previously closed intent can reopen that intent because the previous closure is no longer valid.

### Decision

```text
map create decision <DECISION> \
  [--question <QUESTION_ID>] \
  [--source user|assistant] \
  [--assistant-reasoning TEXT] \
  [--notes TEXT] \
  [--soft]
```

`--source` defaults to `user`.

If `--question` is supplied, the decision becomes that question's answer. A question may have only one current answer.

Assistant-authored decisions require explicit reasoning:

```text
map create decision "Use a 30 minute expiry" \
  --source assistant \
  --assistant-reasoning "Derived from the established security requirements"
```

`--assistant-reasoning` is invalid for `--source user`.

`--soft` marks the decision as deliberately revisit-worthy. Soft decisions prevent affected intent scope from being considered fully closed.

### Idea

```text
map create idea <IDEA>
```

Example:

```text
map create idea "Consider passkey-based recovery later"
```

### Fact

```text
map create fact <FACT> [--made-by user|assistant]
```

`--made-by` defaults to `user`.

Example:

```text
map create fact "The current auth service already supports one-time tokens" --made-by assistant
```

## Relationships

### Relate

```text
map relate <SOURCE_ID> <TARGET_ID>... [--dependent]
```

### Unrelate

```text
map unrelate <SOURCE_ID> <TARGET_ID>... [--dependent]
```

Multiple targets may be supplied in one command. The runtime infers the relationship from the source and target node kinds.

Without `--dependent`:

| Source | Target | Inferred relationship |
| --- | --- | --- |
| intent | intent | `contains` |
| intent | question | `contains` |
| intent | decision | `contains` |
| question | decision | `answers` |
| any node | fact | `fact_context` |
| any node | idea | `idea_context` |

With `--dependent`:

| Source | Target | Inferred relationship |
| --- | --- | --- |
| intent | intent | `depends_on` |
| question | question | `depends_on` |

Question-to-question relationships require `--dependent`.

The runtime rejects illegal shapes, duplicate relationships, removal of relationships that do not exist, multiple current answers to one question, dependency cycles, containment cycles, and other graph-invariant violations.

A successful operation reports the inferred relationships:

```json
{
  "ok": true,
  "operation": "relate",
  "relationships": [
    {
      "kind": "depends_on",
      "source": "...",
      "target": "..."
    }
  ]
}
```

## Setting Map and node properties

`set` has two forms.

Map-level property:

```text
map set <PROPERTY> <VALUE>
```

Node-level property:

```text
map set <ID> <PROPERTY> <VALUE>
```

### Map-level properties

Supported Map-level properties:

```text
map set depth mvp
map set depth thorough
map set stance normal
map set stance adversarial
```

Increasing inherited rigor can reopen previously closed intents whose prior closure was established under the less demanding effective setting.

Specifically, moving inherited depth from `mvp` to `thorough`, or inherited stance from `normal` to `adversarial`, can invalidate prior closure. Intent-level overrides are respected.

### Intent properties

```text
map set <INTENT_ID> explored true|false
map set <INTENT_ID> close true|false
map set <INTENT_ID> depth mvp|thorough|null
map set <INTENT_ID> stance normal|adversarial|null
```

`null` removes the intent-level depth or stance override so the intent inherits the Map-level value again.

Closing an intent is guarded by runtime invariants. `close true` fails if the scope is not actually closable.

An intent cannot close while any of the following applies within its relevant scope:

- the intent itself has not been explored;
- a non-abandoned child intent is still open;
- an intent dependency is unsatisfied;
- a non-abandoned question is unanswered;
- a non-abandoned decision remains soft.

### Question properties

```text
map set <QUESTION_ID> asked true|false
```

### Decision properties

```text
map set <DECISION_ID> soft true|false
```

Making a decision soft can reopen affected intents.

### Keywords

Every node kind supports keywords:

```text
map set <ID> keywords '<JSON_STRING_ARRAY>'
```

Example:

```text
map set 7k2h8s4m1p9x3q6v0abc keywords '["auth","recovery","password reset"]'
```

The value must be a valid JSON array of strings. Shell quoting rules differ by platform.

## Replacing nodes

```text
map replace <OLD_ID> <NEW_ID> --reason <TEXT> [--in-place]
```

Replacement represents semantic succession, not a generic text edit.

Requirements include:

- old and new must resolve to different current nodes;
- they must be the same node kind;
- both must be non-abandoned;
- the new node cannot already be the successor in another replacement history that would merge histories;
- a non-empty reason is required.

The runtime transfers the old node's graph position to the new node and records replacement metadata.

### Normal replacement

Without `--in-place`, the historical old node remains stored but no longer represents the current semantic position.

Commands such as `show OLD_ID` resolve to the current replacement target.

### In-place replacement

With `--in-place`, the old node record is removed while the replacement event remains in history.

Use `history` to inspect either replacement mode.

Replacement may reopen intents when transferred state makes a previous closure invalid.

## Abandoning nodes

```text
map abandon <ID> --by user|assistant --reason <TEXT>
```

Every node kind can be abandoned.

A non-empty reason is required. Abandonment records both actor and reason.

Abandonment is semantic state, not deletion. Abandoned nodes remain inspectable with `show` and may be included by relevant `get` options.

Abandoning a decision that answered a question makes that answer no longer current and can reopen affected intent scope. Abandoning an intent that serves as a dependency can reopen dependent intents.

## Deleting nodes

```text
map delete <ID>... [--force]
```

Deletion is destructive and is deliberately stricter than abandonment.

If any selected node participates in semantic relationships or replacement history, deletion fails unless `--force` is supplied.

The failure reports affected relationships so a caller can review the impact before retrying.

Forced deletion still enforces replacement-history safety. For example, deleting a replacement target cannot silently revive an earlier historical node. The runtime may require the relevant predecessor nodes to be included in the same forced deletion.

Deletion can reopen surviving intents if removing state invalidates prior closure.

Prefer `abandon` when the semantic record should remain part of Map history.

## Reading collections with `get`

`get` returns sorted JSON arrays of node IDs. It does not return full node objects. Follow IDs with `show` or `context` when content is needed.

### Important filter convention

Several `get` flags are inclusion switches rather than exclusive selectors.

For example:

```text
map get intents
```

returns current open, non-abandoned intents by default.

```text
map get intents --closed
```

includes closed intents in addition to the normally returned open intents. It does not mean "closed intents only."

Likewise, `--abandoned` generally includes abandoned nodes instead of meaning "only abandoned nodes," and `get questions --answered` includes answered questions in addition to the normally returned unresolved ready questions.

Where a flag is an actual filter, that is noted below.

### Get intents

```text
map get intents \
  [--id <ID>...] \
  [--explored | --unexplored] \
  [--closed] \
  [--abandoned] \
  [--limit N]
```

Default behavior:

- current IDs only;
- excludes abandoned intents;
- excludes closed intents.

Options:

- `--id` restricts results to the supplied IDs after current replacement resolution.
- `--explored` filters to explored intents.
- `--unexplored` filters to intents not marked explored.
- `--closed` includes closed intents.
- `--abandoned` includes abandoned intents.
- `--limit` truncates the sorted result.

There is currently no dedicated "closed only" switch. Consumers that need only closed intents can request `--closed`, then inspect the returned nodes with `show` and filter on `closed`.

### Get questions

```text
map get questions \
  [--id <ID>...] \
  [--intent <ID>...] \
  [--asked | --unasked] \
  [--answered] \
  [--abandoned] \
  [--include-blocked] \
  [--limit N]
```

Default behavior returns current, non-abandoned, unanswered questions that are ready to ask.

A question is ready only when it is current, non-abandoned, unanswered, belongs to an intent, its question dependencies are satisfied, and the relevant intent dependencies are satisfied.

Options:

- `--id` restricts by question ID.
- `--intent` restricts to questions directly contained by the supplied intents.
- `--asked` filters to questions marked asked.
- `--unasked` filters to questions not marked asked.
- `--answered` includes answered questions.
- `--abandoned` includes abandoned questions.
- `--include-blocked` includes unresolved questions whose dependencies currently block them.
- `--limit` truncates the sorted result.

A useful way to enumerate essentially all current non-abandoned questions for an intent is:

```text
map get questions --intent <ID> --answered --include-blocked
```

### Get decisions

```text
map get decisions \
  [--id <ID>...] \
  [--question <ID>...] \
  [--intent <ID>...] \
  [--soft] \
  [--decided-by user|assistant] \
  [--abandoned] \
  [--limit N]
```

Default behavior returns all current, non-abandoned decisions.

Options:

- `--id` restricts by decision ID.
- `--question` restricts to the current answers for the supplied questions.
- `--intent` restricts to decisions directly associated with the supplied intent: decisions directly contained by it plus answers to questions directly contained by it.
- `--soft` filters to soft decisions only.
- `--decided-by` filters by decision source.
- `--abandoned` includes abandoned decisions.
- `--limit` truncates the sorted result.

`--intent` is direct rather than recursive. For recursive intent-scope decision discovery, use `context <INTENT_ID>` and its `scopeDecisions` field.

### Get ideas

```text
map get ideas [--id <ID>...] [--abandoned] [--limit N]
```

Default behavior returns current, non-abandoned ideas.

### Get facts

```text
map get facts \
  [--id <ID>...] \
  [--made-by user|assistant] \
  [--abandoned] \
  [--limit N]
```

Default behavior returns current, non-abandoned facts.

`--made-by` filters by fact provenance.

## Showing nodes

```text
map show <ID>...
```

With one ID, `show` returns one JSON object. With multiple IDs, it returns a JSON array of objects.

Historical replacement IDs resolve to their current node.

Every node output contains its `id` plus its serialized semantic fields.

Common fields include:

```text
id
kind
text
keywords
abandoned
abandonedReason   when abandoned
abandonedBy       when abandoned
```

Intent-specific fields can include:

```text
context
explored
closed
depth
stance
```

The runtime also computes:

```text
effectiveDepth
effectiveStance
```

`effectiveDepth` and `effectiveStance` account for Map-level inheritance when an intent has no override.

Question-specific fields can include:

```text
reason
asked
answered
ready
```

`answered` and `ready` are computed from current graph state.

Decision-specific fields can include:

```text
source
assistantReasoning
notes
soft
```

Fact-specific output includes:

```text
madeBy
```

Ideas have the common node fields without kind-specific semantic fields.

## Reading local graph context

```text
map context <ID>
```

`context` returns the current local semantic neighborhood around a node.

It is current-state oriented and rejects an abandoned focused node.

The payload contains:

```text
node
parents
children
dependencies
dependents
facts
ideas
```

For a question with an answer, it also contains:

```text
answer
```

For an intent, it additionally contains recursive scope indexes:

```text
scopeQuestions
scopeDecisions
```

### Context field meanings

- `node`: the full `show`-style representation of the focused current node.
- `parents`: direct containment parents, plus the answered question when the focused node is a decision answer.
- `children`: direct `contains` children.
- `dependencies`: outgoing dependencies with each target ID and a computed `satisfied` boolean.
- `dependents`: IDs that directly depend on the focused node.
- `facts`: fact IDs attached from the focused node through `fact_context`.
- `ideas`: idea IDs attached from the focused node through `idea_context`.
- `answer`: the current answer decision ID when the focused node is an answered question.
- `scopeQuestions`: all non-abandoned current questions contained anywhere in the focused intent subtree.
- `scopeDecisions`: all non-abandoned current decisions associated anywhere in the focused intent subtree.

`facts` and `ideas` represent outgoing contextual attachments from the focused node. `context` is not a generic reverse-edge dump.

## Status

```text
map status
```

`status` summarizes the selected Map and returns fields including:

```text
path
runtimeVersion
schemaVersion
depth
stance
nodes
historicalReplacements
session
```

`nodes` contains counts for each node kind, split between current non-abandoned nodes and abandoned current nodes.

Example shape:

```json
{
  "path": ".../.map",
  "runtimeVersion": "...",
  "schemaVersion": "2",
  "depth": "thorough",
  "stance": "normal",
  "nodes": {
    "intent": {
      "current": 3,
      "abandoned": 0
    }
  },
  "historicalReplacements": 2,
  "session": false
}
```

`session` only reports whether recovery state currently exists.

## Validation

```text
map validate
```

Validation checks runtime and semantic graph invariants, including:

- schema/runtime compatibility;
- node-kind field validity;
- abandonment metadata consistency;
- relationship endpoint validity;
- duplicate or illegal relationship shapes;
- historical nodes incorrectly participating in current relationships;
- self dependencies;
- intent containment cycles;
- intent and question dependency cycles;
- multiple current answers to a question;
- replacement-chain consistency;
- validity of closed intents.

Successful validation:

```json
{
  "ok": true,
  "errors": []
}
```

Consumers preparing a handoff should validate before treating a Map as reliable input.

## Search

```text
map search <QUERY> [--limit N] [--include-history]
```

`--limit` defaults to `10`.

Search returns a ranked JSON array of node IDs.

Search is case-insensitive after whitespace normalization and considers:

- node text;
- intent context;
- question reason;
- assistant decision reasoning;
- decision notes;
- keywords.

Exact normalized text and exact keyword matches receive strong preference, followed by phrase and token overlap.

Abandoned nodes are excluded from search. Historical replacement nodes are also excluded by default.

Use:

```text
--include-history
```

to allow historical replacement nodes to participate in search results.

Search returns IDs only. Follow a result with `show`, `context`, or `history` as appropriate.

## Replacement history

```text
map history <ID> [--limit N]
```

`history` follows the replacement chain associated with the supplied ID.

It returns:

```text
root
current
nodes
events
```

- `root` is the earliest ID in the discovered replacement chain.
- `current` is the current resolved node ID when the chain resolves successfully.
- `nodes` lists each ID in chain order together with its node representation when that historical record still exists.
- `events` contains replacement metadata such as old ID, new ID, reason, mode, and creation time.

For an in-place replacement, a historical node entry may have `node: null` because the old node record was deliberately removed while the replacement event was retained.

## Recovery sessions

Recovery sessions exist so the Map workflow can survive context loss or interruption. They are not a second semantic database.

External tools that only consume Map intent should use graph state rather than session state.

### Initialize recovery state

```text
map session init
```

Fails if a recovery session already exists.

A new session begins with:

```text
summary:   empty
depth:     6
exchanges: empty
pending:   none
```

### Read or set summary

Read:

```text
map session summary
```

Set:

```text
map session summary <TEXT>
```

Summary whitespace is normalized. The summary is limited to 2200 Unicode characters.

### Read or update exchanges

Read retained exchanges:

```text
map session exchange
```

Append a user message:

```text
map session exchange -u <TEXT>
map session exchange --user <TEXT>
```

Append an assistant message:

```text
map session exchange -a <TEXT>
map session exchange --assistant <TEXT>
```

Set retention depth:

```text
map session exchange --depth N
```

`--user` and `--assistant` conflict with each other in one invocation. Exchange depth must be at least `2`. When retained exchanges exceed the configured depth, the oldest exchanges are dropped.

### Read, set, or clear pending work

Read:

```text
map session pending
```

Set:

```text
map session pending <TEXT>
```

Clear:

```text
map session pending --clear
```

### End recovery state

```text
map session end [--force]
```

A session with pending work cannot be ended normally. `--force` bypasses that guard and is intended only when the pending work has been explicitly abandoned.

## Depth and stance

Map-level depth values:

```text
mvp
thorough
```

Map-level stance values:

```text
normal
adversarial
```

Intents can override either value. `show` reports both the stored override, when present, and the computed effective value.

These settings are semantic workflow metadata. The runtime enforces their persistence and reopening effects, while the Map skill defines how they influence discovery behavior.

## Question readiness

Question readiness is computed by the runtime and exposed through `show` and the default behavior of `get questions`.

A question is ready when all of the following are true:

- it is a current question;
- it is not abandoned;
- it is unanswered;
- it belongs to at least one current intent;
- each question it depends on is answered or abandoned;
- relevant ancestor intent dependencies are satisfied.

For intent dependencies, the prerequisite intent must be non-abandoned and closed.

This allows external consumers to distinguish unresolved questions that are actionable now from unresolved questions that are intentionally blocked by prerequisites.

## Intent closure

`closed = true` is a runtime-enforced semantic claim, not merely a status label.

A current, non-abandoned intent can close only when:

1. it has been marked explored;
2. every non-abandoned child intent in its recursive scope is closed;
3. relevant intent dependencies are satisfied;
4. every non-abandoned question in scope is answered;
5. every non-abandoned decision in scope is hard rather than soft.

Changes that make an existing closure stale can automatically reopen the affected intent or its ancestors. Examples include adding unresolved questions, adding dependencies, making a decision soft, abandoning an answer, increasing effective rigor, replacing graph state, and some relationship or deletion changes.

External consumers should therefore trust the current `closed` value rather than assuming a previously observed closure remains valid forever.

## Recommended read-only handoff flow

A downstream implementation or issue-tracker agent can consume a completed Map without invoking `$map` and without knowing the Map skill's subagent workflow.

A practical read-only sequence is:

1. Resolve the intended Map and inspect its status.
2. Validate it.
3. Enumerate current intents, including closed ones.
4. Inspect relevant root or focus intents with `show` and `context`.
5. Follow `scopeQuestions`, `scopeDecisions`, dependencies, facts, and ideas as needed.
6. Read the corresponding nodes with `show`.
7. Use `search` for targeted retrieval and `history` only when provenance through replacement matters.
8. Build tracker-native work from the resulting semantic information without mutating Map.

Example:

```text
map --path /path/to/project status
map --path /path/to/project validate
map --path /path/to/project get intents --closed
map --path /path/to/project context <INTENT_ID>
map --path /path/to/project show <QUESTION_ID> <DECISION_ID>
```

For a completed intent, `context` is particularly useful because it exposes recursive `scopeQuestions` and `scopeDecisions` IDs while preserving the focused node's dependency and contextual relationships.

The handoff consumer remains responsible for understanding its own destination, such as Beads, GitHub Issues, Jira, or another tracker. Map only supplies the settled intent graph through its public read interface.

## Read-only command summary

| Command | Primary use |
| --- | --- |
| `status` | Identify Map/runtime state and high-level counts |
| `validate` | Verify graph invariants before consumption |
| `get` | Enumerate current node IDs with filters |

## Mutation command summary

| Command | Primary use |
| --- | --- |
| `init` | Create a new `.map` |
| `create` | Create intent/question/decision/idea/fact nodes |
| `relate` | Add an inferred semantic relationship |
| `unrelate` | Remove an inferred semantic relationship |
| `set` | Change supported Map or node properties |
| `replace` | Record semantic succession from one node to another |
| `abandon` | Retire a node while preserving history |
| `delete` | Destructively remove stored nodes |

## Compatibility guidance for integrations

For integrations that consume Map programmatically:

- Invoke the CLI rather than the embedded database.
- Parse JSON stdout for normal runtime commands.
- Treat node IDs as opaque.
- Run `validate` and inspect its `ok` field before a consequential handoff.
- Prefer current, non-abandoned state unless historical provenance is explicitly needed.
- Use `context` for relationships rather than attempting to reconstruct the graph from database files.
- Do not treat recovery session state as settled user intent.
- Do not assume `get` inclusion flags are exclusive filters; follow the semantics documented above.
- Use `map --version` and `status.runtimeVersion` when compatibility matters.
- Use built-in `--help` as the final authority for syntax supported by the installed runtime version.
